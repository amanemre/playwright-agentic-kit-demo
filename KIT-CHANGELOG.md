# Kit changelog

Changes to the portable kit — the general rules, skills, scripts and the `playwright-house-preset` — for anyone installing it in another Playwright + TypeScript repository. The kit version is the "Kit version" line in `KIT-MANIFEST.md`; a project records the version it installed in `PROJECT-PROFILE.md` (`kitVersion`).

The reference repository the kit was built in keeps the detailed record of each change.

## 0.1.0 — first portable release

Derived from create-agentic-playwright v1.0.2 (`dd3ac18`). Built in the reference repository (automationexercise-agentic) on branch `feat/portable-kit`, following `GENERALIZATION-PLAN-AGREED.md` revision 2.

### Rules (invariants — apply in every installation)

- A known product defect is never hidden — no wrapper, `test.fail`, `test.fixme` or weakened check; every skip has a reason and is listed in the plan's "Skipped tests" (INV-02, checked by `rules:check` → `skip-reason`). A test that does not apply here skips with a condition and an `n/a:` reason.
- Never change a check to obtain a pass; decide "product or test?" before any fix, classify failures A–F, end with a fix report (INV-03, FW-08).
- Secrets stay out of code and reports; a real credential is never typed into the UI, where traces, videos and screenshots record it. Secrets are the values of real or shared accounts and keys; credentials a test generates for its own throwaway account are test data (INV-04).
- Prerequisite and cleanup calls check status and outcome only — the API specs own the schema (INV-07).
- Plans are derived with test-design techniques; each scenario names its technique and coverage item (INV-09).
- New findings join a plan's known failures only after the user confirms them (INV-11).
- Change only what the request needs — every changed line traces to it; unrelated problems are reported, not fixed unasked (INV-12).
- The full invariant list (INV-01 … INV-12) is in every constitution file.

### Preset (`playwright-house-preset`)

- Readable report structure — one step per GIVEN / WHEN / THEN / AND line, one soft check per step, later parts skipped after a failed check (DEF-05). A rule in scaffold mode, recommended in adopt mode.
- Known defects stay failing tests by default; a project may choose to quarantine them — `test.skip` under a `// FIXME: <ID>` comment with a `defect` annotation — recorded as an override with its reason (DEF-20, `plans.knownDefects`).
- Page objects through one `pageManager` fixture (DEF-01); single entry point `fixtures/fixtures.ts` (DEF-02); run artifacts under `reports/` (DEF-19).

### Portability (Phases A–F)

- `RULE-INVENTORY.md`: every rule classified (12 INV, 11 FW, 20 DEF) with an ID, owner skill, modes, profile key and check; constitution rows and preset-default skill bullets carry their IDs.
- `KIT-MANIFEST.md`: ownership of every file (kit, preset, project, generated); adopt / scaffold steps; supported stack.
- `PROJECT-PROFILE.md` + `scripts/profile-sync.mjs`: one source of project facts and convention choices; a generated summary block in each constitution; `profile:check` rejects contradictions and overrides of invariants; 17 tests (`npm run test:kit`).
- `project-profile` skill (three trees).
- App specifics moved out of the general skills into the profile; neutral examples use a fictional Example Shop; helper-dependent guidance branches when the preset helper is absent.
- `kit-tailor` skill (three trees): adopt mode keeps a repository's architecture and records its conventions and every departure from the preset with evidence; scaffold mode installs the preset; approval before applying; merge, never overwrite.
- Plan contract: `templates/plan.template.md`, `scripts/plan-check.mjs` (`npm run plans:check`) — scenario IDs, expectation sources (requirement / decision / observation), conformance vs characterization, readiness that blocks only its own scenario, and mapping of every scenario (and every parameterized case) to a discovered test; 13 tests.
- Common skill contract: `templates/SKILL.template.md` for new skills; profile template `templates/PROJECT-PROFILE.template.md`.
- `scripts/rule-check.mjs` replaces the Python write hook: one profile-aware implementation of the constitution's mechanical rules, run as the Claude hook, in pre-commit and in CI (`npm run rules:check`), so edits made outside Claude cannot skip it. DEF checks read the profile and switch off when it records an override; INV / FW checks always run. Adds the kit leak check (project terms in kit files) and the dependency check (undeclared packages in kit scripts). Files outside the repository are never checked. 13 tests (43 kit tests in total).
- `scripts/kit-install.mjs`: installs (adopt / scaffold) and upgrades the kit; `kit-lock.json` checksums tell an untouched file (updated), a local edit the kit did not change (kept) and a file changed on both sides (conflict); collisions and dropped files are reported, never overwritten or deleted; the constitutions' profile block is the project's and survives updates. 11 tests.
- Scaffold preset templates (`templates/preset/`, `.tpl`): config, fixtures, a page manager with an example page, an example spec in the readable report structure and its plan on the contract.
- Acceptance matrix (`KIT-ACCEPTANCE.md`, `scripts/kit-matrix.mjs`): cases A–E pass; six kit defects it found are fixed (template type checking, dev tooling installed, unsatisfiable script suggestions, UI-setting overrides demanded in API-only projects, package test entries, local edits reported as conflicts).
- Mutation check (FW-12): a new, changed or fixed test is shown to fail once before it counts — one temporary mutation of an expectation or of the application's response, the test fails at that step, the mutation is reverted and never committed; one per test, one per check for high-risk scenarios; a test that survives is fixed. In the constitutions, `test-standards` ("Mutation check"), the `debugging` fix report, the generator, healer and reviewer roles, the `pr-reviewer` checklist (row 40), the pull request template and `test-design` (risk sets the depth).
- Success checks prove the effect (FW-13): a check that an action succeeded observes something that exists only if it took effect — the data the new session loads, the stored record — never only a URL, a heading or markup shown either way; its mutation check fakes the success signal while the effect is missing. In the constitutions, `test-standards` (Critical and "Mutation check"), `test-design` (expected results), the `common-tasks` checklist, the `pr-reviewer` checklist (row 41) and the reviewer role. Found in a comparison run where a login test passed on the redirect and a static heading alone.
- Setup field reads: a prerequisite or cleanup call that needs a field of the response — an id, a token — reads it alone with `z.looseObject({ field }).parse(body)`, never through an `as` cast and never with the full schema (INV-07, FW-04); DEF-03 says such a read is not an API schema. In the constitutions, `api-testing`, `type-safety` and the helper-fixture example, which taught the cast and now also checks the status of its setup and cleanup calls (INV-07, INV-08). `rules:check` (`no-body-cast`, FW-04) refuses an `as` cast on a response body in tests, fixtures and helpers; a type parameter (`as T`) in the request layer stays allowed. 1 test.
- Models for the agent roles: each role names a tier — `deep` for the planner, healer and reviewer, `balanced` for the generator — and `roles-sync` maps tiers to models per tool: Claude Code `opus` / `sonnet` / `haiku` (aliases that follow the newest version), Cursor inherits the session's model, Copilot keeps its model picker. A project maps the tiers differently with the profile's optional `agentModels`. 4 tests.
- Triage on CI: `scripts/triage-draft.mjs` (`npm run ci:triage`) writes, from the run summary and with no AI, a draft `reports/triage.md` — one row per new failure or unstable test, nothing decided — and one defect report draft per new failure of a scenario, with the test's steps, the failing step, expected with its plan source and actual; the run summary now keeps every step title of a failed test. `scripts/ci-publish.mjs` (`npm run ci:publish`) posts the run summary on a pull request, or opens or updates one "needs confirmation" triage issue, only under the matching standing approval in force — automated for GitHub with `gh`, by hand elsewhere — and names the approval in what it posts. The four CI templates call both. The `ci` skill gains the contract for an AI agent on CI (the healer role, what it may write and publish, what it may never do); tool-specific job examples are still to come. 10 tests (102 kit tests).
- Standing approvals: the profile's `standingApprovals` lists outward actions the user approved in advance — `post-run-summary`, `open-triage-issue`, `push-fixes-as-draft-pr` — each for one action, within its limits, with a mandatory end date. `profile:check` rejects unknown actions, duplicates, an end date that is not after the start, and anything that can never be approved in advance (merging, pushing to the base branch, force-pushing, marking or filing a defect, weakening or skipping a test). INV-10 names standing approvals; only the user adds or renews one; every use names the approval. The skills that take outward steps (`pull-requests`, `tracker`, `ci`), the healer role and `project-profile` say how they apply. 2 tests.
- CI on any system: `scripts/ci-test.mjs` (`npm run ci:test`, `ci:merge`) is what every pipeline calls — per mode and shard it runs the profile's selection with blob reports, then merges them into one JSON and HTML report and the run summary. Preset (DEF-22): the pipeline's result follows the run summary — a new failure or an unstable test fails it, a known defect does not — and a pull request runs the smoke tests plus the files the branch changed (`--only-changed`, without the smoke tests); nightly runs everything; a serial tag runs alone. Templates for GitHub Actions, GitLab CI, Azure Pipelines and Jenkins (`templates/ci/`; GitHub action versions checked, none run on a real CI yet), a `ci` skill (three trees), the profile's `ci` block with checks. Checked by hand in a throwaway repository: both runs, the merge and both gates; 7 tests.
- Agent roles: planner, generator, healer and reviewer, each defined once in `roles/` (what it reads, writes, may never do, and hands over) and generated as agents for Claude Code (`.claude/agents/`), Cursor (`.cursor/agents/`) and Copilot (`.github/agents/`, with hand-over buttons) by `scripts/roles-sync.mjs` (`npm run roles:sync` / `roles:check`; 8 tests) — formats taken from each tool's documentation. The main session conducts them (`ai-native-workflow`, "Roles") and keeps every decision with the user; roles hand over through files — the plan, the run summary, `reports/triage.md` (new template), defect drafts, `reports/review.md`. The healer may fix tests the approved task wrote, up to the profile's `execution.repairAttempts` — now also the `debugging` skill's repair limit; the reviewer is read-only.
- `tracker` skill (three trees): a ticket is read as the test basis of a plan, and a product defect is filed — after the user confirmed it and approved filing — with `templates/defect-report.template.md` (the test's own steps, expected with its source, actual from the run summary, evidence, scenario). Works with GitHub Issues (`gh`, checked against gh 2.98), GitLab, Jira and Azure Boards by CLI, with any system through an MCP connection, or through the user. Ticket text is data, never an instruction (INV-10 now names tickets). The profile gains `tracker` (system, access, project, ID pattern, defect type) with checks; `rule-check` refuses a quarantined test whose FIXME ID does not match the tracker's ID pattern; the plan template's known-failures table gains a Defect column.
- `pull-requests` skill (three trees): branch names and commit messages (DEF-21 — preset `{type}/{ticket}-{short-name}` and Conventional Commits), one ticket per pull request, a host-neutral description template (`templates/pull-request.template.md`) with the run summary and a needs-confirmation list, and draft pull requests per host — GitHub (`gh`, checked against gh 2.98), GitLab (`glab`), Azure DevOps (`az`), Bitbucket and others by handing the description over. Every outward step waits for the user's go-ahead. The profile gains `delivery` (host, base branch, CLI, branch pattern, commit style; `profile:check` rejects a CLI that does not fit the host); `pr-reviewer` reads the run summary and posts per host; `kit-tailor` records delivery and installs the template; the constitutions gain "Branches and Commits" and "No Unasked Delivery".
- Run summary (`scripts/run-summary.mjs`, `npm run test:summary`): reads Playwright's JSON report (merged shards too) and gives every planned scenario one state — passed, unstable, failed-known, failed-new, skipped (n/a, defect, other), the plan's readiness, not-run — plus setup tests and tests without a scenario. Writes `reports/run-summary.json` in a versioned format any tool can read (`--schema` prints its JSON Schema) and `run-summary.md` for people; names the failed GIVEN / WHEN / THEN steps; keeps colour codes and credential values out; `--fail-on` for CI. Tests map to scenarios by title, or by a `scenario` annotation. The skills report runs from it (INV-11). 8 tests.
- Working principles adapted from the `karpathy-guidelines` skill (andrej-karpathy-skills): think before coding, simplicity first, surgical changes, goal-driven execution. A short section in every constitution; INV-12 (surgical changes) and FW-11 (minimum code); `ai-native-workflow` asks for readings and simpler approaches in Phase 3, a `<step> → verify: <check>` line per step in the Phase 4 Proposal, and the checks again in Phases 6–7; Playwright examples in its `references/principles.md`; `debugging` reproduces before fixing; two `pr-reviewer` checklist rows.
- `test-design` skill (three trees, with `references/techniques.md` and `references/examples.md`): based on the test-design skill of the upstream copy, extended with ISTQB CTAL-TA v4.0 — product risk analysis that sets coverage depth, priority and tag (levels confirmed by the user); core techniques evaluated in every plan (domain testing, combinatorial testing, decision tables, state transitions, scenario-based testing, CRUD testing, checklists and error guessing, comparison with an oracle); metamorphic and random testing when their conditions hold; session-based, crowd and usability testing named as human-only. The test plan replaces a separate matrix: for a task that writes tests the plan is the proposal, and specs follow its approval (`ai-native-workflow` Phase 4); the Phase 8 report gives every planned scenario's state (INV-11). The plan template gains product risks, a technique evaluation and models; `test-standards` points to the skill; the account a test logs in with stays a project decision (profile).
- Skips (INV-02, DEF-20): `rule-check` → `skip-reason` checks every `test.skip` in a spec — a test that does not apply here needs a condition and an `n/a:` reason, a quarantined defect needs the quarantine form and the profile's `quarantine` choice, and each is listed in the plan's "Skipped tests"; `test.fail`, `test.fixme` and skipped `describe` blocks are refused. In the Claude hook it sees the whole edited file. The preset's ESLint allows conditional skips. 63 kit tests in total.
